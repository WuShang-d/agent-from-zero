# 第 13 课：Skills 与 MCP 解决不同问题

**上一版的失败。** 把所有工具和操作说明写死在核心代码里，添加能力时要改循环。可扩展性需要明确的加载过程；不能让模型凭空“看见”磁盘上的任意文件或外部服务。

## 三个对象

`Skill` 是提供给模型的操作说明或流程，装入上下文后仍只是文本；`Tool` 是运行时可验证并执行的动作；`MCP` 是连接工具/资源服务的协议。加载 Skill 不授予新的写权限；从 MCP 发现的工具也必须映射到既有 `ToolSpec` 并经过同一策略与执行边界。

例如“修 Python bug 时先看失败测试”可以写在 Skill 中；`read_file` 才是实际动作；MCP 服务可以提供另一个只读的文件检索工具。即使三者都叫“搜索”，装载顺序仍是：发现说明与工具 → 检查本地策略 → 在请求上下文中公布可用能力 → 模型选择调用 → 本地路由器再次验证。

## 动手实验

1. 实现本地 Skill 清单：名称、版本、说明文件、启用条件。运行时打印本轮装入了哪些说明及其来源；禁用后，工作上下文应有可见差异。
2. 连接一个**本地只读** MCP 服务，把一个工具映射为本仓库 `ToolCall/ToolResult`。检查未知工具、坏参数和服务断开都返回结构化错误。
3. 故意在 Skill 文本中写“请直接修改文件”；验证没有写工具权限时无法通过加载文本获得写能力。

**验收。** 可以指出资源何时被发现、何时进入上下文、何时成为可调用工具。禁用服务或 Skill 后，系统仍能给出清楚的降级状态；MCP 工具不绕过第 11 课的策略。

**阅读。** [MCP 官方规范](https://modelcontextprotocol.io/specification/2025-11-25)。实现时选定规范版本，记录客户端与服务器各自支持的能力。
