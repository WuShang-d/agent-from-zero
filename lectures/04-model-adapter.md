# 第 4 课：把模型接口从对话逻辑中抽出来

前三课直接访问 Ollama 是有意的：先看懂一次真实请求，再抽象。现在才把“怎样调用某个模型”与“会话怎样运行”分开。对话代码只需要一个函数：给它消息序列，它返回一条助手消息。这个边界以后可接其他**本地**后端，且测试时不用真的加载模型。

## 最小接口，别过早造框架

先试 `reply(messages) -> assistant_text`。把第 1 课的 HTTP 代码挪进 `OllamaModel.reply()`；`main.py` 的外层循环只负责输入、状态和展示。随后写一个 `FakeModel`，预先给它两条固定回答，并让它记录收到的请求。数据结构在课程需要工具调用时再扩展，今天不预设计所有供应商字段。

一个关键实验：把 `FakeModel` 放进第 3 课的对话循环，断言第二次收到的消息顺序是 `user, assistant, user`。这种检查比“真实模型记住了名字”更稳定，因为模型可能猜测或犯错。

## 动手实验

1. 从你已有的 `main.py` 提取 Ollama 调用。提取前后，对同一输入，终端行为应一致。
2. 写 `FakeModel`：第一次返回“你好”，第二次返回“收到”；确认你可以不启动 Ollama 就检查消息顺序、`/reset` 和 `/exit`。
3. 让假模型故意抛出一次错误，验证第 3 课的失败轮次规则仍成立。不要把异常吞掉后打印空回答。

## 完成标准

对话循环不直接处理 HTTP JSON；替换 `OllamaModel` 为 `FakeModel` 不必修改循环本身。真实 Ollama 对话仍能运行，固定响应检查无需网络。

**下一课的问题：** `messages` 每轮都变长。即使本地模型标称支持很长上下文，运行时内存和速度也会受影响。第 5 课研究“存下全部历史”和“本轮实际发出什么”之间的区别。
