# 第 12 课：中断、恢复与“结果不明”

**上一版的失败。** 事件日志能显示历史，不意味着可以安全恢复执行。进程可能在写文件成功后、写入 `tool_completed` 事件前崩溃；重放相同调用会产生第二次副作用。

## 用状态而不是猜测恢复

给每次工具调用记录 `planned → started → completed/failed`，并在完成事件中保存效果摘要或文件摘要。重启时将调用分为三类：确认未开始、确认已完成、结果不明。前两类可按规则继续；“结果不明”的写入需核对实际文件状态或交给用户处理，不能盲目重放。用户在运行中追加“只读”要求，应作为新的事件进入下一轮，并立即更新权限策略。

一个关键时间线：`seq=10 tool_started(c1)` → 文件确实写入 → 进程崩溃 → 没有 `tool_completed`。事件只能证明 c1 开始过；文件 diff 可能证明写入发生，但不能由日志单独推断结果。恢复器应把这类调用停在 `outcome_unknown`，记录核对结论后再推进。只读工具在明确幂等且可重复时可以有不同恢复策略。

## 动手实验

1. 在工具开始前强制退出并恢复：下一次运行只执行尚未开始的动作，事件序号继续递增。
2. 在写入完成后、完成事件落盘前强制退出：恢复器显示 `outcome_unknown`，要求核对练习目录的实际 diff；确认前不再次写入。
3. 运行途中发出“后续只读”，再让假模型请求写入，检查策略确定性拒绝。把取消和追加限制区分：取消结束当前 turn，追加限制改变后续上下文与策略。

**验收。** 任何恢复路径都能解释每次副作用是否发生、证据是什么；同一个完成的写入不会因为程序重启自动执行两次。恢复的不是终端文字，而是由事件与环境状态共同确定的任务状态。

**源码阅读。** [Codex 仓库](https://github.com/openai/codex)与 [App Server 文章](https://openai.com/index/unlocking-the-codex-harness/)可用于比较任务、轮次、事件的生命周期。只借设计问题，不假设仓库的当前内部类型名永远不变。
