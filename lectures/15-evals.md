# 第 15 课：用固定任务检验 Harness 是否真的变好

**上一版的失败。** 一次演示成功无法证明系统可靠；新增 Memory、Compaction 或子 Agent 后，成本可能上升，成功率却没有改善。模型主观说“已完成”也不能当作任务成功。

## 设计可复现的任务

先做少量但覆盖不同失败模式的任务，再扩充：纯问答、多轮事实、错误工具参数、越界读取、取消恢复、长上下文、练习项目中的确定 bug。每个任务保存初始文件快照、用户目标、允许的操作、期望观察、评分脚本和模型配置。对代码修复任务，用测试结果和最终 diff 判断；对权限任务，用**没有越界副作用**判断；对恢复任务，用事件轨迹和文件状态判断。

固定 bug 任务的一个严格判定是：修复前 `test_fractional_average` 失败，运行后该测试通过，`test_empty_input` 仍通过，而且 diff 只触及允许文件。单看“测试通过”不够：Agent 可能删除测试或改变断言。评分器要从干净快照安装原始测试，再验证最终文件和事件轨迹。

## 动手实验

1. 固定一组任务，重复运行基线版本与加入新模块的版本。记录 `task_id、代码版本、模型配置、随机性设置、是否成功、失败类型、调用次数、耗时、可得 token 用量、批准次数`。
2. 选择至少一个失败案例逐事件分析：模型意图、路由校验、实际执行、观察、最终结论分别是什么。评分脚本与原始轨迹同时保存，人工判断的部分单独标记。
3. 分别关闭 Memory、Compaction、子 Agent 重跑适用任务；不要把不同模型、不同任务或不同文件快照的结果直接当作 Harness 效果比较。

**毕业演示。** 在受控练习目录中定位并修复一个确定 bug，运行测试，展示 diff；中断后恢复，并解释哪些动作未重放、哪些结果仍需人工确认。提交完整轨迹和失败案例，而不是只提交一段成功终端录屏。

**阅读。** [SWE-bench 论文](https://arxiv.org/abs/2310.06770)用于学习任务与环境设计；[Anthropic《Demystifying evals for AI agents》](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)用于设计评测循环。本课程不声称已经运行这些基准。
