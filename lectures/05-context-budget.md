# 第 5 课：保留历史，不等于每轮全发给模型

第 3 课的 `messages` 随对话无限增长。模型每轮真正看到的，是程序这一次请求里的消息；长期保存的会话历史可以比这个工作上下文更长。现在把两个概念拆开：`history` 记录发生过的事，`working_context` 是本轮准备发给模型的子集。

## 先做简单、可解释的选择

新建 `build_context(history, current_user, budget)`。先保留当前用户请求与系统规则，再从近到远选完整的历史轮次。第一版可以用字符长度做**保守估算**，但报告里必须叫“估算单位”，不能叫精确 token 数。若当前请求本身太长，明确报错；不要悄悄截断用户任务。真实 token 计数可以以后针对选定模型补上。

例如预算 100 单位，预留回答 20，系统规则占 15、当前问题占 25，历史还剩 40。最近三轮各占 18，只能纳入两轮；原始 `history` 的三轮仍都在，较早的一轮只是本次没有进入 `working_context`。

## 动手实验

1. 用 `FakeModel` 收到的请求证明：预算足够时顺序完整，预算变小时较早轮次被舍弃，当前问题仍在。
2. 打印 `included` 和 `dropped` 的轮次编号。相同输入必须得出相同结果。
3. 让当前问题单独超过预算，确认程序明确告诉用户“本轮请求太长”，且原始历史未被改坏。

## 完成标准

能回答“这句话在历史里吗？”与“模型这次看见了吗？”两个不同问题。观察长历史时的请求大小和响应速度，但不要只凭一次运行下性能结论。
